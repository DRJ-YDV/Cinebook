# CineBook initial workflow inventory

Inspection date: 25 October 2026. This is the baseline before this audit's application changes. Status reflects source inspection and previously executed TMDB checks, not unexecuted end-to-end tests.

## Architecture discovered

React 19 with TanStack Start and TanStack Router file routes, React Query, TypeScript, Tailwind and Radix UI. TanStack server functions dynamically import MongoDB repositories and the TMDB/Razorpay server modules. MongoDB uses the official Node driver with a global pooled client. No test command, test framework or automated suite exists initially. The directory has no Git metadata; no commits or history operations are planned.

Collections: users, theatres, screens, shows, show_seats, bookings, payments, favorites, offers, meta. Existing user roles are stored on users. Encrypted cookie sessions contain a user ID but initially have no persistent revocation record. Credentials are server environment variables. The configured default production target is an edge preset despite MongoDB requiring a Node runtime.

## Features and workflows

- **Registration/login — BROKEN (security).** `/login` → store login/signup → signIn/signUp → users. PBKDF2 is implemented, but outages create/use plaintext local accounts; identity/role are restored from localStorage. Validators are mostly TypeScript casts. Required tests: invalid/duplicate signup, unknown email/password, session rotation/expiry/logout, role injection, no plaintext persistence.
- **Admin identity/dashboard — WORKING WITH LIMITATIONS.** `/admin` → getAdminAccess/getAdminOverview → users/bookings/theatres/screens/shows/offers. Analytics has a server role check. Other admin mutations lack equivalent checks; ADMIN_EMAILS auto-promotes matching registrations. Required tests: anonymous 401, normal user 403, trusted admin allowed, local role editing ineffective, controlled admin setup.
- **Profiles — BROKEN (access control).** `/profile` → updateUserProfile/getUserProfile → users. Client user IDs select records; optimistic success can hide failures. Required tests: user A/B reads/updates, unknown input properties, persistence, visible failure.
- **Favorites — BROKEN.** Movie card/detail → store.toggleFavorite → addFavorite/removeFavorite → favorites. Client IDs establish ownership; MongoDB write failures are ignored; shared local list leaks across accounts; page does not hydrate from MongoDB. Required tests: add/remove/duplicate/concurrent requests, refresh/new session, guest and cross-user access, missing TMDB details.
- **My bookings — BROKEN (status/ownership gaps).** `/bookings` → getUserBookings → bookings, merged with local mirrors. Server lists use session identity, but browser data may still label pending/failed records confirmed and cancellation reports false local success. Required tests: two sessions, manipulated IDs, pending/cancelled state, persistence/failure.
- **Booking detail/ticket/QR — BROKEN.** `/ticket/$bookingId` reads local bookings and generates client QR/text. getBooking endpoint is public. Pending/failed tickets can be represented as confirmed from client state. Required tests: owner/stranger/guest, confirmed-only issuance, refresh/new device, mutable browser state.
- **TMDB lists/details/search — WORKING WITH LIMITATIONS.** `/`, `/movies`, `/movie/$movieId`, `/upcoming` → TMDB server functions → external API; no MongoDB movie metadata. Prior live check returned 20 items per list and build/type checks passed. Bounded retry, visible sample fallback and short recovery were just implemented. Required tests: actual lists/search/details/media, failure recovery, no secret exposure.
- **Theatres/screens — WORKING WITH LIMITATIONS.** `/theatres`, movie showtime UI → theatre/screen server reads → theatres/screens. Some UI uses bundled fallback even after a valid empty response. saveTheatre has no admin check. No full screen-management UI exists. Required tests: availability, relationships, admin mutation denial, empty/error states.
- **Showtimes — BROKEN (trust boundary).** Movie details → generated show ID/client hint → ensureShow/createShow → shows/screens/theatres. Client hints can choose price/date/screen/movie; public creation can overwrite shows. Required tests: invalid/expired date, screen relationship, persisted authoritative price, altered hints, admin-only creation.
- **Seat selection/holds — BROKEN (integrity).** `/book/$showId` → getAvailableSeats/reserveSeats/releaseSeats → show_seats. Atomic reservation exists, but complete seat IDs/hold ownership/expired confirmation and unique-index enforcement need repair. UI masks failures with mock availability. Required tests: two simultaneous claimants, invalid seat, expired hold, reallocated seat, query consistency.
- **Booking creation — BROKEN (security).** Checkout → createBooking → shows/seats/bookings/payments/offers. Session assignment partly exists, but guest path, arbitrary hints/pricing, status and repeat-request behavior require repair. Required tests: authoritative ownership/amount, duplicate submission, invalid seat/offer, partial-write compensation.
- **Razorpay — BROKEN (bypasses), external checkout NOT YET TESTED.** Checkout → createRazorpayOrder/verifyRazorpayPayment → provider and bookings/payments/show_seats. HMAC exists, but direct confirmBooking accepts client PAID, standalone order accepts client amount, ownership is missing on payment endpoints, failed signatures mutate records, and capture/amount verification needs inspection. Required tests: order binding, HMAC/invalid signature, capture/amount/currency, repeated callback, failure/expiry. No real payments authorized.
- **Cancellation/refunds — BROKEN.** `/bookings` → cancelBooking → bookings/payments/seats. Ownership partially checked; cancellation marks REFUNDED without gateway refund and has unsafe state races. Required tests: owner only, repeated cancel, payment/cancel race, honest refund-pending state, seat release.
- **Offers — WORKING WITH LIMITATIONS.** `/offers` and checkout → getOffers/saveOffer and repository pricing → offers/bookings. Public saveOffer is unprotected; bundled client discounts may differ from server amounts; expiry/eligibility need verification. No redemption tracking implemented. Required tests: unauthorized edits, authoritative discount, unknown/expired offer.
- **Notifications/preferences — WORKING WITH LIMITATIONS.** Header/profile/upcoming reminders → store → localStorage. Device-local only, shared across accounts; no server notification delivery/scheduler exists. Required tests: user scoping/logout, no claim of real scheduled notifications.
- **Admin management features — NOT IMPLEMENTED where absent.** There are no full user-management, screen-management, movie-management, booking-management or CRUD dashboard interfaces; do not call absent UI broken. Existing server mutations must still be protected.
- **Deployment/logging/errors — WORKING WITH LIMITATIONS.** `.env.example`, Vite preset, server error wrapper and repository error mapper. Node build command uses POSIX environment assignment incompatible with PowerShell; generic errors may become DB_UNAVAILABLE and trigger unsafe fallback. Unique-index errors are swallowed. Required tests: Node artifact/start, safe errors, missing env behavior, schema/index setup without deleting data.

## Workflow map

Public movie browsing: route loader → React Query → TMDB server function → server credentials → HTTPS request/cache → mapped Movie → registry/UI. Failure must be labeled and recoverable.

Private data: UI action → validation → server function → verified session → current database user → owner-scoped query/write → safe response → account-scoped React state/cache → visible persisted result. Baseline profile/favorites/ticket/payment paths do not consistently follow this chain.

Booking/payment: selected show/seats → server validation/authoritative pricing → atomic temporary hold → owned pending booking/payment → provider order → verified signature plus matching captured payment → conditional hold commitment → confirmed database booking → owner-checked ticket. Baseline includes bypasses and client-only success paths.

## Safe execution constraints

No live account mutation, destructive seeds/migrations, credential changes, real payment, production deploy or data reset. Runtime tests use separate sessions and isolated fixtures; mocked and live evidence will be labeled separately. External checkout/capture and live MongoDB integration remain unverified until their prerequisites are established.
